# 작업지시서 — 상세 경로 잔여 지연 24.4초 (측정 먼저)

배경: PR #312 로 시즌 레일 예열이 들어가 콜드 페이지가 141.23초 → 24.36초로 줄었다.
레일 8건은 전부 504 → 전부 200(234~671ms)으로 완전히 해결됐다.
**남은 24.4초는 상세 요청 하나(`includeAnalysis=true`)가 전부 차지한다.**

원인은 명확하다. #312 의 예열 대상이 `_v2_player_summary_index`(요약 경로)뿐이었고,
상세 경로 `build_player_detail` 은 예열 대상이 아니었다. 지시서 범위가 좁았던 것이지
구현이 틀린 게 아니다.

## 단계 1 — 측정. 이걸 건너뛰지 마라

**"예열하라"는 지시가 아니다. 먼저 24.4초가 어디에 쓰이는지 분해해라.**

`build_player_detail` 이 콜드로 도는 동안 구간별 소요 시간을 계측해서 보고해라. 최소한 이 구분:
- 컨텍스트/코호트 적재 (선수와 무관하게 그 시즌·모드·스코프·대회 전체에 대해 한 번 드는 비용)
- 해당 선수 개별 계산 (선수마다 드는 비용)

**이 비율이 처방을 가른다:**
- 컨텍스트 적재가 대부분이면 → 컨텍스트만 예열하면 되고, 그러면 **모든 선수가** 빨라진다
- 선수별 계산이 대부분이면 → 예열로는 못 푼다. 어느 선수를 예열할지 고를 방법이 없기 때문이다
  (선수가 수천 명이다). 그 경우 계산 자체를 줄이거나 사전계산으로 가야 한다

**측정 없이 대상을 고르지 마라.** 오늘 이미 "쿼리가 느리다"는 기록이 실측으로 반증된 전례가 있다.

계측은 임시 코드로 해도 되고, 결과만 보고하고 계측 코드는 남기지 않아도 된다.
숫자를 보고하면 내가 다음 지시를 낸다.

## 단계 2 — `warm_cache` 로그가 프로덕션에 안 찍힌다 (이건 지금 고쳐라)

배포는 성공했는데 Render 로그에 `warm_cache_scheduled` / `warm_cache_context_complete` /
`warm_cache_complete` 가 **하나도 안 나온다.** 로컬에서는 나온다.

**원인은 확정됐다. 추가 조사 없이 바로 고쳐라.**

`api_server/` 어디에도 로깅 설정이 없다. `logging.basicConfig` 도 `dictConfig` 도 호출하지 않는다.
따라서 `messi.warm_cache` 와 `messi.player_summary` 는 루트 로거로 전파되는데 **루트에 핸들러가 없다.**
파이썬의 lastResort 핸들러는 **WARNING 이상만** 내보낸다. 그래서:

| 호출 | 결과 |
|---|---|
| `WARM_CACHE_LOG.info(...)` | **조용히 버려짐** |
| `WARM_CACHE_LOG.exception(...)` | ERROR 라 stderr 로 나옴 |

**실제 관측과 일치한다**: 프로덕션 로그에 `player_summary_timeout`(`.warning()`)은 찍혔지만
`player_summary_complete`(`.info()`)는 한 번도 안 찍혔다. `warm_cache_scheduled` 도 전부 INFO 라 사라졌다.

**고칠 것**: `messi` 부모 로거에 핸들러를 붙이고 레벨을 INFO 로 설정해라.
uvicorn 이 자기 로거를 따로 구성하므로 그것과 충돌하지 않게, 핸들러가 이미 있으면 중복으로 붙이지 마라.
`messi.warm_cache` 와 `messi.player_summary` 둘 다 이 부모를 쓰므로 한 번에 해결된다.
환경변수로 레벨을 조절할 수 있게 하면 좋다(예: `API_LOG_LEVEL`, 기본 INFO).

**이게 왜 중요한가**: 예열이 실제로 도는지, 몇 초 걸리는지, 실패했는지를 지금은 알 수 없다.
운영 중 예열이 조용히 깨져도 아무도 모른다. 무음 실패를 하나 더 만들지 마라.

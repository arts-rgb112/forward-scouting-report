## 1. 배경 — 왜 고치는가 (실측 근거)

`build_tactical_summary` (`api_server/service.py` L2485-2532)의 세 줄이 전부 **기준선 없는 하드코딩 절대 임계값**이다.

**(a) 죽은 분류가 존재한다.** 전체 10,412행 중 `cca <= 35` 아래가 **100%** → "넓은 활동 반경형"은 한 명도 나올 수 없다. `in_box >= 30`도 97%가 미달 → 사실상 전원 "박스 외곽 연계형".

실제 사례: 화면에 뜬 "핵심 반경 균형형 23.0%"는 **리그 상위 8%**다. 라벨이 정보를 주는 게 아니라 반대로 오해를 시킨다.

**(b) 하프스페이스형은 구조적으로 분류 불가.** 리그 평균 레인 분포가 균등하지 않다:

```
lane_1 22.13 / lane_2 16.09 / lane_3 22.79 / lane_4 17.66 / lane_5 21.32
```

절대값 `max()`를 쓰므로 평균 대비 **+9%p**인 하프스페이스가 평균 대비 **+3%p**인 중앙에게 진다.

**(c) CCA가 표본 수에 끌려다닌다 (순수 편향, 실험으로 격리).** 같은 선수 150명, 움직임 동일, 좌표 수만 변경:

```
20개 → 8.38%   45개 → 11.27%   90개 → 13.53%   135개 → 14.57%   180개 → 15.16%
```

**1.81배 차이.** 원인: `continuous_core.py`가 고정 32×22 격자 + 고정 `[1,4,6,4,1]` 커널을 쓴다. 표본이 적으면 밀도가 몇 칸에만 몰려 면적이 작게 나온다. 표본적응 대역폭(h는 n의 -1/6승에 비례)은 1.81→1.51배로 줄일 뿐 **불충분**하다.

**(d) 대회 스코프를 넘어 비교하면 안 된다.** 좌표를 정확히 180개로 맞춘 뒤에도 유럽대항전 CCA가 전 포지션에서 약 5%p 낮다 (Striker 15.9→11.4, DM 18.6→13.1, CB 14.1→10.2). 균일한 이동이므로 전술 차이가 아니라 대회 구조 차이(유럽 6~10경기 vs 리그 30경기+).

### 재진단 금지 (이미 확인된 정상 동작)

- 저장 좌표는 **180개 상한**이며 76.6%가 정확히 180개다
- CSV `cca_area_pct`는 저장 좌표 재계산과 **100% 일치**한다 → 보라색 등고선과 숫자는 같은 데이터에서 나온 게 맞다. **이 부분은 버그가 아니다**
- CSV `sample_points`는 상한 적용 **이전** 개수라 CCA와 상관이 높게 보인다. 이것도 버그가 아니다

## 2. 작업 A — CCA 산식 교체 (점수 영향 있음)

### A-1. 산식

`continuous_core.py`에 **고정표본 재추출(fixed-N resampling)** 경로를 추가한다.

| 파라미터 | 값 | 근거 |
|---|---|---|
| 기준 좌표 수 N | **60** | 모집단의 **90.6%**를 같은 자로 측정 (120이면 86.1%) |
| 반복 추출 R | **20** | 재현성 r = **+0.9922** 확보 |
| 집계 | R회 추출의 `coreAreaPct` **평균** | |
| 난수 시드 | **고정** | 재실행 시 같은 값이 나와야 한다 |

좌표 N개 미만 선수: **자기 좌표 전체로 현행 방식대로 계산한 값을 그대로 쓴다** (발주자 결정).

- 점수 모집단에서 제외하지 않는다. `MISSING_COMPONENT_SCORE`를 주지 않는다
- 다만 **API 응답에 `low_sample: true`와 실제 좌표 수를 실어** 화면에서 표시할 수 있게 한다

**격자(32×22)와 스무딩 커널은 변경하지 않는다.** 프론트 `HEATMAP_COLUMNS` / `HEATMAP_ROWS`와 묶여 있어 범위가 커진다.

### A-2. 예상 점수 영향 (검증 완료 — 이 범위를 벗어나면 중단하고 보고)

CCA의 최종 가중치는 **7.5%**다.

```
M.E.S.S.I. = 0.30·box + 0.20·outside_box + 0.15·danger + 0.15·space + 0.10·duel + 0.10·press
space      = 0.50·CCA + 0.50·danger_zone_density
→ CCA 실질 가중치 = 0.15 × 0.50 = 7.5%
```

2025/2026 8대리그 1,752명 시뮬레이션 기준:

- CCA 백분위 순위 상관 **r = +0.9959**
- CCA 백분위 변동: 중앙값 1.52점 / p90 4.51점 / **최대 9.54점**
- **최종 M.E.S.S.I. 점수 변동: 최대 1.5점 이내, 2점 넘게 움직이는 선수 0명**

> ⚠️ 위 수치는 좌표 120개 기준 시뮬레이션이다. N=60으로 구현한 뒤 **실제 변동을 다시 측정해 이 범위 안인지 확인**하고 보고할 것.

### A-3. ETL 재계산

`cca_area_pct`를 새 산식으로 재산출한다 (`data/tactical_3zone_ratio.csv`, 10,412행).

**주의:** SportsAPI 수집 작업이 `data/harvest/`에서 동시 실행 중이다. 경로가 겹치지 않지만 **재계산 전 수집 프로세스 상태를 확인**할 것.

## 3. 작업 B — 전술 요약 재설계 (화면만, 점수 무관)

### B-1. 공통 규칙

| 항목 | 규칙 |
|---|---|
| 비교 기준 | **동일 포지션 × 동일 대회 스코프**의 중앙값·백분위 |
| 포지션 정규화 | 기존 **`_benchmark_position_key` 재사용**. 표기만 정규화하고 역할 의미를 병합하지 않는다 ("Striker"와 "forward"는 별개 유지 — 현행 정책) |
| 최소 코호트 | **20명** (`BENCHMARK_RADAR_V2_MINIMUM_POSITION_POPULATION` 재사용) |
| 미달 시 | `low_sample` — 값은 보여주되 표시. **숨기거나 전체 평균으로 몰래 대체 금지** |
| 스코프 분리 | 8대리그(7,307행) / 유럽대항전 UCL·UEL·UECL(3,105행). **통합 평균 하나로 퉁치기 절대 금지** |
| 계산 위치 | **전부 서버.** 브라우저에서 평균·백분위 계산 금지 |

데이터 조인은 검증 완료: `tactical_3zone_ratio.csv` ↔ `spear_cohort.csv` (`fotmob_player_id` ↔ `player_id`) **77% 성공**, 포지션+좌표 충분한 행 6,978건. 주요 포지션은 양 스코프 모두 20명을 넉넉히 통과하고, **유럽대항전 풀백·윙백만 미달**이라 `low_sample` 대상이다.

### B-2. 세 줄 재작성 — 모든 줄이 `값 → 기준선 → 차이 → 백분위` 4조각을 갖는다

| 줄 | 산출 방식 | 출력 예 |
|---|---|---|
| 볼 받는 구역 | `in_box_ratio` vs 동포지션·동스코프 중앙값 | "박스 안 활동 16.0% — 8대리그 스트라이커 중앙값 16.0%와 동일 (상위 50%)" |
| 침투 레인 | **평균 대비 편차가 가장 큰 레인** 선택 (절대 `max()` 폐기). 상위 2개까지 표기 | "좌측 하프스페이스에 평균보다 +9.1%p 많이 위치 (상위 8%). 다음은 중앙 +3.0%p" |
| 활동 반경 | 새 CCA vs 동포지션·동스코프 백분위 | "핵심 활동 반경 23.0% — 8대리그 스트라이커 중 상위 8%" |

**라벨은 분포 백분위에서 파생시킨다. 하드코딩 절대 임계값을 전부 제거한다.**

예: 상위 20% → "넓은 활동 반경형", 하위 20% → "좁은 활동 반경형", 그 외 → "동포지션 평균권". 이렇게 하면 죽은 분류가 **원리적으로** 생길 수 없다.

**참고:** N=60으로 바꾸면 표시되는 CCA 절대값이 현재보다 낮아진다(같은 선수라도 좌표를 적게 쓰므로). **기준선도 같은 산식으로 산출**하면 비교는 정상이다. 화면의 값과 기준선이 **반드시 같은 산식**에서 나와야 한다.

## 5. 검증 게이트 (프로덕션 배포 전 전부 통과해야 함)

1. **점수 변동 실측 보고** — 최종 M.E.S.S.I. 점수 변동이 **최대 1.5점 이내 / 2점 초과 0명**인지 확인. 벗어나면 **중단하고 보고**
2. **티어 경계 이탈 집계** — 표시 점수(정수 내림)와 티어(Diamond Lv.1 등)가 바뀌는 선수 수를 **반드시 세어서 보고**. 이건 사용자 눈에 가장 크게 보이는 변화다
3. **죽은 분류 부재 확인** — 새 라벨 체계에서 **모든 라벨이 실제로 출현**하는지 전수 확인 (현재는 "넓은 활동 반경형"이 0명)
4. **하프스페이스 분류 확인** — 하프스페이스 편차가 가장 큰 선수가 실제로 하프스페이스형으로 분류되는지 표본 확인
5. **스코프 분리 확인** — 8대리그 선수가 유럽 기준선과 비교되지 않는지 확인
6. **빌드 검증은 `tsconfig.build.json` 기준** (`npm run build`). `tsconfig.app.json`으로 하면 테스트 파일의 무관한 기존 타입 오류가 섞여 나온다
7. **QA URL에 반드시 `?taxonomy=` 포함.** 빠뜨리면 플래그와 무관하게 구형 보드로 조용히 폴백되어 설정 오류처럼 보인다
   예: `/players/194165?season=2025%2F2026&mode=league&scope=7&competition=all&taxonomy=duel-press-v1`
8. **V1 동반 확인** — `continuous_core.py` 변경이 `app.py`를 깨뜨리지 않는지
9. 로컬 검증으로 끝낸다. Preview 배포를 QA용으로 소모하지 않는다
   로컬 백엔드: `MESSI_CORS_ORIGINS="http://localhost:5173,http://127.0.0.1:5173" python -m uvicorn api_server.main:app --host 127.0.0.1 --port 8000`

## 6. 배포

- feature flag로 **fail-closed** (프로젝트 관례). 화면 변경(B·C)은 플래그로 되돌릴 수 있어야 한다
- **CCA 산식 변경(A)은 플래그로 되돌릴 수 없다** — ETL 산출물이 바뀌기 때문. 롤백 경로를 **미리 문서화**하고 이전 CSV를 보관할 것
- Vercel 환경변수는 **Sensitive라 읽을 수 없다. "못 읽음 = 꺼짐"으로 절대 추정하지 말 것.** 실제 값은 배포된 동작(네트워크 요청 파라미터·렌더된 DOM)으로 판정한다
- **push / merge / 프로덕션 배포는 발주자 승인 후에만 실행한다**

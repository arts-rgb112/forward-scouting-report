# 작업지시서 — Slack 감시기 상주화 + DM 감시 + 즉시 반응

발주자 지시 2026-09-04: *"감시기를 보강하고 dm 및 채널로 코덱스에서 난리칠때 바로바로 응답하게 만들어"*

## 문제 (근본 원인)

지금 감시기는 Claude 스크래치패드의 `slack_watch.py` 이고 구조가 **exit-on-hit** 이다 —
메시지를 하나 감지하면 프로세스가 **종료**되고 Claude 가 수동으로 다시 띄워야 한다.
그 재기동 사이가 전부 사각지대다. 게다가 스크래치패드는 세션 임시 폴더라 세션이 바뀌면
스크립트도 상태파일도 사라진다. 저장소에 없으니 코덱스가 고칠 수도, 이력을 남길 수도 없다.

그리고 **45초 폴링**이라 코덱스가 막혀서 도움을 요청해도 최악 45초 + 재기동 대기만큼 늦는다.

## 요구사항

### 1. 상주화
- 감시기를 저장소 안으로 옮긴다(`messi-2-dashboard/`, `agent_loop.py` 옆).
- **종료하지 않는 상주 프로세스.** 감지해도 죽지 않는다. 예외가 나면 로그만 남기고 다음 사이클로 간다.
- 종료는 명시적 신호(SIGINT / 파일 플래그)로만.
- 상태파일(이미 알린 스레드 ts·커밋 SHA)을 저장소 기준 경로로 옮겨 재시작해도 중복 알림이 없게 한다.
  기존 `slack_watch_alert_state.json` 중복방지 로직은 그대로 계승.

### 2. 즉시 반응 — 폴링 말고 이벤트 구동
- **PR #310 에서 이미 만든 Slack Socket Mode 브리지를 재사용해라.** 새로 만들지 마라.
  Socket Mode 는 WebSocket 이라 메시지가 오는 즉시 이벤트가 뜬다 — 폴링 지연이 없어진다.
- 폴링은 **백업 경로로만** 남긴다(소켓이 끊겼을 때). 주 경로가 아니다.

### 3. DM 감시 추가
- 지금은 `#자동사냥` 채널만 본다. **봇/코덱스가 보내는 DM 도 같이 감시**한다.
- 채널이든 DM 이든 동일하게 처리한다.

### 4. "난리칠 때" 를 정의해서 즉시 에스컬레이션
아래가 뜨면 **지연 없이** Claude 에게 DM 으로 깨움 신호를 보낸다:
- 코덱스가 실패·에러·예외를 보고했을 때
- 코덱스가 질문했거나 승인/판단을 요구했을 때(막혀서 멈춘 상태)
- 의견/티켓 한도 초과로 코덱스가 손 놓았을 때
- 기존 4종 정체 감지(A 디스패치 · B 워크트리 · C 의견한도 · D 승인대기)는 기능 유지

### 5. 반드시 지킬 경계 — 자동 응답 금지
- 감시기는 **깨우는 데까지만** 한다. **코덱스에게 자동으로 답을 쓰지 마라.**
- `[PASS]`/`[REJECT]`/`[REVISE]`/`[APPLY]` 판단은 Claude(사법) 몫이다. 감시기가 대신 내리면
  삼권분립이 깨진다. 감지 → 요약 → Claude 호출, 거기서 끝이다.
- 예외로 허용되는 자동 동작은 **읽음 표시 👀 리액션 하나뿐**이다
  (발주자는 리액션을 쓰지 않기로 확정됐으므로 `ginger` 계정 반응은 무조건 Claude 것으로 해석된다).

### 6. Claude 에게 넘기는 요약은 짧게
- 원문을 통째로 넘기지 마라. **채널·스레드 ts·작성자·상태·핵심 한두 줄**만 넘긴다.
- 이유: 원문 전체는 Claude 컨텍스트 비용이 크다. 실제로 채널 통째 읽기 한 번이 이 프로젝트에서
  가장 비싼 단일 동작이었다. 감시기가 Slack 을 대신 읽어서 요약만 주는 게 이 설계의 핵심 이점이다.

## 금지

- `agent_loop.py` 의 실행 경로·태그 파싱(`SLACK_ACTION_RE`) 로직은 건드리지 마라. 별건이다.
- 새 라이브러리 추가 금지 — Socket Mode 브리지가 이미 있다.

**참고**: 이 프로젝트에서 무음 실패는 반복 사고다 — `RECORDED NOTHING`(백틱 때문에 승인이 죽음),

2. 리터럴 텍스트 `@codex` (대소문자 무시)

### 다만 두 방향은 구조가 다르다 — 이걸 구현이 흡수해야 한다

`@claude` 는 **감시기가 읽고 판단하는 마커**다. 감시기가 어차피 전 채널을 읽으므로 어떤 형태든 잡힌다.

`@codex` 는 다르다. 지금 코덱스에게 메시지가 **물리적으로 도달하는 경로**는 Slack 의 `app_mention`
이벤트 하나뿐이고, 그건 **정식 봇 멘션이 있어야만** 발생한다. 리터럴 `@codex` 텍스트로는
이벤트 자체가 안 간다 — 오늘 실제로 그래서 `[APPLY]` 하나가 무음으로 사라졌다.

**따라서 감시기가 다리를 놓는다:**
- 감시 채널 메시지에 실행 태그(`[APPLY]`·`[PLAN]`·`[REVISE]` 등)가 있고 `@codex` 호출이
  리터럴 형태로만 있어(정식 봇 멘션이 없어) `app_mention` 이 발생하지 않은 경우,
  **감시기가 `agent_loop` 의 디스패치 경로를 직접 호출**해서 실행시킨다.
- 정식 봇 멘션이 있으면 기존 경로 그대로 두고 중복 실행하지 않는다(§A 의 `instruction_id` dedup 준수).
- 어느 경로든 §7 의 90초 접수 확인은 그대로 적용한다.

**이 설계의 목적**: 멘션 누락으로 인한 무음 실패를 **구조적으로 불가능하게** 만드는 것이다.
지금은 발행자가 멘션을 빠뜨리면 아무 신호 없이 사라진다. 이 다리가 놓이면 리터럴 호출로도 도달한다.

### 최종 대칭표

| | Claude → Codex | Codex → Claude |
|---|---|---|
| 호출 신호 | `@codex` (정식 멘션 또는 리터럴) | `@claude` (정식 멘션 또는 리터럴) |
| 전달 주체 | Slack `app_mention`, 없으면 감시기가 중계 | 감시기 |
| 태그 어휘 | `[APPLY]`·`[PLAN]`·`[REVISE]`·`[DISCUSS]`·`[STOP]`·`[RESET]` | `[DONE]`·`[FAIL]`·`[BLOCKED]`·`[ASK]`·`[LIMIT]`·`[NOTE]` |
| 접수 증거 | `SLACK → AGENT` 로그 | Claude 의 👀 (감시기가 자동으로 달아도 되는 유일한 동작) |
| 미접수 감지 | 90초 (§7) | 90초 (§7) |
| 중복 방지 | `instruction_id` + `supersedes` | `instruction_id` + `reply_to_message_ts` |
| 상태 | `queued→running→waiting→terminal` | 동일 |

## 13. `[티켓추가 N]` — 발주자가 예산을 즉석에서 늘린다 (2026-09-04 발주자 확정)

발주자 원문: *"브레인샤워에서 티켓 추가할 때 내가 그냥 `[티켓추가 2]` 이런 식으로 쓰면
코덱스가 알아먹게 세팅 좀. 너무 복잡하더라."*

이건 세션 초반 지적 *"코덱스는 티켓 초과되면 손 빨고 있잖아"* 의 정식 해결책이다.
지금은 `#brainshower` 의견 모드가 응답 2회에서 끝나고, 더 논의하려면 새 스레드를 파야 한다.
그건 맥락이 끊기고 발주자가 불편하다.

### 문법 — 외울 게 하나여야 한다

```
[티켓추가 2]     → 그 스레드에 2회 추가
[티켓추가]       → 1회 추가 (숫자 생략 시 기본값)
[티켓 추가 3]    → 공백 허용, 동일하게 처리
```

대소문자·공백에 관대하게 파싱해라. 발주자가 형식을 기억하려 애쓰게 만들지 마라.

### 동작

- **적용 범위는 그 메시지가 놓인 스레드**다. 채널 전체가 아니다.
- **이미 예산이 소진돼 멈춘 스레드에도 소급 적용한다.** 이게 핵심이다 — 한도에 걸려 멈춘 스레드를
  다시 굴리는 게 목적이므로, 추가되면 코덱스가 **그 자리에서 이어서 답해야 한다.**
  추가해놓고 다음 메시지를 기다리게 만들면 기능이 무의미하다.
- `#brainshower` 의견 모드와 `#자동사냥` 실행 턴 예산 **양쪽 다** 적용한다.
- 부여 즉시 그 스레드에 **확인 답글**을 남긴다: 부여량과 남은 예산을 숫자로.
  발주자가 먹혔는지 추측하게 만들지 마라.

### 권한과 상한 — 오타·자가증식 방어

- **발주자(`U0BU7BTNLJK`)가 쓴 것만 유효하다.** 코덱스가 스스로 예산을 늘리는 건 명백한 구멍이다.
  봇이 쓴 `[티켓추가]` 는 무시하고 그 사실을 로그에 남겨라.
- **1회 부여 상한 5, 스레드 누적 상한 10.** 초과 요청은 **조용히 무시하지 말고**
  상한까지만 부여한 뒤 "요청 N, 부여 M, 상한 때문" 을 답글에 밝혀라.
  `[티켓추가 100]` 같은 오타가 예산을 태우는 걸 막되, 무음 실패는 만들지 않는다.
- 상한을 넘겨야 할 진짜 이유가 있으면 그건 발주자가 다시 쓰면 된다. 자동으로 뚫지 마라.

### 왜 상한을 두는가

이 프로젝트에서 토큰은 실제 제약이다. 발주자가 오늘 두 번 지적했다
("티켓만 다 쓰잖아", "슬랙 채널 읽는 것도 토큰 드냐"). 예산 증액은 **명시적 행위**여야 하고,
한 번의 오타로 무제한이 되면 안 된다.

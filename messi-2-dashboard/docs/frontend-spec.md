# M.E.S.S.I. 2.0 프론트엔드 요구사항 명세

## 1. 문서 목적과 기준

이 문서는 FUTBIN 리더보드의 시각적 밀도와 다크 테마를 참고한 M.E.S.S.I. 2.0 선수 스카우팅 대시보드의 다음 설계·구현 단계를 위한 기준이다. 현재 저장소의 `MessiScoutingDashboard.tsx`, `README.md`, 최초 사용자 요구사항, 이전 프론트엔드 리뷰 내용을 기준으로 작성했다.

이번 파이프라인의 기본 범위는 **실행 가능한 프론트엔드 프로토타입의 품질 향상**이다. 실제 선수 API, 인증, 서버 저장, 에셋의 법적 검수와 배포는 별도 범위다.

## 2. 제품 목표

사용자는 한 화면에서 많은 공격수 후보를 빠르게 검색·필터링하고, 핵심 지표의 강약을 즉시 파악한 뒤, 2~4명을 비교하거나 관심선수로 저장할 수 있어야 한다.

핵심 성공 경험은 다음과 같다.

1. 첫 화면에서 점수, 티어, 주요 지표 및 선수 정체성을 즉시 이해한다.
2. 이름뿐 아니라 클럽·리그·국가로도 원하는 선수를 빠르게 좁힌다.
3. 지표의 의미와 점수 구간을 화면을 떠나지 않고 확인한다.
4. 후보 2~4명을 선택해 동일 지표 기준으로 비교한다.
5. 관심선수를 저장하고 새로고침 후에도 다시 확인한다.

## 3. 사용자와 주요 사용 시나리오

### 주요 사용자

- 다수 공격수 후보를 빠르게 스크리닝하는 스카우트/분석가
- 특정 선수의 프로필과 상대적 강점을 확인하는 의사결정자
- 모바일에서 후보 목록을 간단히 확인하는 현장 사용자

### 주 사용자 플로우

```text
진입
→ 헤더/범례로 평가 맥락 확인
→ 선수·클럽·리그·국가 통합 검색
→ 포지션/관심선수 필터 및 정렬
→ 목록에서 점수와 핵심 지표 스캔
→ 지표 설명 툴팁 확인
→ 관심선수 저장 또는 비교 후보 선택
→ 2~4명 상세 비교
→ 비교 후보 수정/초기화 또는 탐색 계속
```

### 예외 및 복구 플로우

- 결과 없음: 적용된 조건과 검색어를 확인하고 개별 필터 칩 또는 전체 초기화로 복구한다.
- 비교 인원 1명: 상세 비교 버튼이 비활성화되고 1명을 더 선택하라는 안내가 보인다.
- 비교 인원 4명: 추가 선택은 거부되고 사용자에게 최대 인원을 알린다.
- 저장소 접근 실패: 관심선수 기능은 현재 세션에서 계속 동작하고 앱 전체는 중단되지 않는다.
- 이미지 로드 실패: 레이아웃이 깨지지 않는 대체 표현이 보여야 한다.

## 4. 기능 요구사항

### F-01 고밀도 선수 목록

- 데스크톱에서는 고밀도 테이블로 선수 프로필, 티어, M.E.S.S.I. 점수, 5개 지표, 출전시간, 나이, 비교/저장 액션을 표시한다.
- 선수 프로필에는 페이스온, 선수명, 국기, 리그, 클럽 아이콘, 포지션을 포함한다.
- 테이블 첫 열과 헤더는 긴 목록/가로 스크롤에서도 맥락을 유지할 수 있어야 한다.
- 행 hover와 키보드 focus가 구분되어야 한다.

### F-02 통합 검색

- 검색 대상은 선수명, 클럽명, 리그명, 국가명이다.
- 검색은 대소문자와 발음 구별 부호를 무시한다. 예: `Mbappe`로 `Mbappé` 검색.
- 입력 즉시 목록과 결과 수를 갱신한다.
- 검색어 지우기와 전체 필터 초기화가 제공되어야 한다.

### F-03 필터와 정렬

- 데이터에서 파생된 포지션 필터를 제공한다.
- 관심선수만 보기 토글을 제공한다.
- 기본 정렬은 M.E.S.S.I. 점수 내림차순이다.
- 최소 정렬 옵션은 점수, 이름, 나이다.
- 활성 조건을 칩 형태로 표시하고 각 조건을 개별 제거할 수 있어야 한다.

### F-04 동적 점수 색상

- 90~100: 네온 그린.
- 80~89: 밝은 녹색.
- 70~79: 주황색.
- 0~69: 빨간색.
- 색상은 텍스트와 테두리/저채도 배경에 일관되게 적용한다.
- 색상만으로 의미를 전달하지 않고 숫자와 범례를 함께 제공한다.

> 최초 문구는 `60점 이하`만 빨간색으로 명시해 61~69 구간이 비어 있다. 현재 구현과 연속 구간 원칙에 따라 0~69를 빨간색으로 해석한다. 이는 중대한 범위 변경은 아니며 후속 확인 시 임계값만 조정할 수 있어야 한다.

### F-05 지표 툴팁

- 각 지표 값에 hover 또는 키보드 focus 시 지표명, 현재 점수, 설명을 표시한다.
- 툴팁은 다른 셀이나 화면 밖으로 잘리지 않아야 한다.
- 스크린리더가 값과 설명의 연관 관계를 인식할 수 있어야 한다.

### F-06 티어와 마이크로 에셋

- 티어는 텍스트 대신 `<img>` 기반 아이콘을 기본 표현으로 사용한다.
- 최소 티어는 diamond, gold, silver를 지원한다.
- 티어 아이콘에는 접근 가능한 대체 텍스트 또는 인접 접근성 레이블을 제공한다.
- 선수/국가/리그/클럽 이미지는 지연 로딩하며 실패 시 레이아웃을 유지하는 fallback을 제공한다.

### F-07 선수 비교

- 사용자는 선수 2~4명을 선택해 비교할 수 있다.
- 선택 상태는 각 행/카드와 하단 고정 비교 트레이에 동기화된다.
- 트레이는 선택된 선수, 현재 인원, 개별 제거, 전체 제거, 상세 비교 열기/닫기를 제공한다.
- 상세 비교는 M.E.S.S.I. 점수와 5개 핵심 지표를 동일 축으로 나란히 보여준다.
- 4명을 초과해 선택하면 상태를 바꾸지 않고 접근 가능한 알림을 제공한다.

### F-08 관심선수

- 각 선수는 관심선수에 추가/제거할 수 있다.
- 상태는 `localStorage`에 유지되어 새로고침 후 복구된다.
- 저장 성공/제거 상태를 시각적 메시지와 `aria-live`로 알린다.
- 손상되거나 유효하지 않은 저장값은 무시한다.

### F-09 빈 결과와 상태 피드백

- 검색 결과가 0명일 때 원인을 이해할 수 있는 제목과 안내를 표시한다.
- 전체 필터 초기화 버튼을 제공한다.
- 검색 결과 수를 항상 표시한다.
- 피드백은 화면을 가리지 않고 일정 시간 후 사라지며 스크린리더에도 전달된다.

## 5. 데이터 계약

### 프론트엔드 도메인 모델

```ts
type Tier = "diamond" | "gold" | "silver";
type MetricKey =
  | "boxThreat"
  | "dangerZone"
  | "linkPlay"
  | "pressing"
  | "progression";

type AssetRef = {
  name: string;
  icon: string;
};

type Player = {
  id: number;                  // 데이터셋 내 유일하고 안정적인 식별자
  name: string;
  role: string;               // 현재 입력 형식: "CF / LW"
  age: number;
  minutes: number;
  tier: Tier;
  score: number;               // 0..100
  face: string;
  nation: AssetRef;
  league: AssetRef;
  club: AssetRef;
  stats: Record<MetricKey, number>; // 각 값 0..100
};
```

### 계약 규칙

- `id`는 관심선수/비교 상태 복원의 키이므로 데이터 갱신 사이에도 안정적이어야 한다.
- `score`와 모든 `stats`는 유한한 0~100 숫자여야 한다.
- `age`와 `minutes`는 0 이상의 정수여야 한다.
- `role`은 현재 UI 호환을 위해 `/` 구분 문자열을 허용하되, 실제 API 연결 시 `roles: string[]`로 정규화하는 것을 권장한다.
- 이미지 URL은 HTTPS 또는 앱 내부 정적 경로여야 한다.
- 화면 컴포넌트가 샘플 상수를 직접 소유하지 않도록 다음 구현 단계에서 `players`를 props 또는 별도 데이터 모듈 경계로 분리하는 것을 권장한다.
- 로딩/오류/빈 데이터 상태를 추가할 수 있도록 데이터 소스 인터페이스를 확장 가능하게 설계한다.

### 에셋 수집기와의 연결 계약

- 에셋 종류는 `players`, `clubs`, `nations`로 분리한다.
- 프론트엔드는 수집기 원본 파일명을 직접 추론하지 않고, 최종 URL/경로가 매핑된 데이터만 소비한다.
- 라이선스와 attribution 정보는 프론트 표시 여부와 별개로 manifest에 보존한다.

## 6. 상태 모델

| 상태 | 타입 | 초기값 | 지속성 | 규칙 |
|---|---|---:|---|---|
| `query` | string | `""` | 없음 | 정규화 후 통합 검색 |
| `role` | string | `"ALL"` | 없음 | 데이터 파생 옵션 중 하나 |
| `sort` | enum | `"score"` | 없음 | score/name/age |
| `watchOnly` | boolean | false | 없음 | watchlist와 교집합 |
| `watchlist` | number[] | `[]` | localStorage | 중복 불가, 유효 ID만 허용 |
| `compare` | number[] | `[]` | 없음 | 선택 순서 유지, 0~4명 |
| `compareOpen` | boolean | false | 없음 | 비교 2명 미만이면 실질적으로 닫힘 |
| `feedback` | string | `""` | 없음 | 단기 상태 알림 |

파생 상태는 별도 저장하지 않는다.

- `filteredPlayers`: query + role + watchOnly 적용 후 sort.
- `comparedPlayers`: compare ID 순서에 따라 Player로 해석.
- `hasFilters`: 기본 상태와 다른 검색/필터/정렬 유무.
- `positions`: 전체 데이터의 role로부터 생성.

권장 불변식:

- `watchlist`와 `compare`에는 중복 ID가 없다.
- `compare.length <= 4`.
- 데이터에서 사라진 ID는 복원 시 제거한다.
- 비교 인원이 2명 미만이 되면 상세 비교 패널은 닫는다.

## 7. 반응형 요구사항

### 모바일: 320px 이상, `md` 미만

- 테이블 대신 카드 목록을 사용한다.
- 선수 정체성, M.E.S.S.I. 점수, 최소 3개 핵심 지표, 비교/관심 액션을 한 카드 안에 제공한다.
- 필터 컨트롤은 여러 줄로 래핑되고 터치 대상은 최소 44×44 CSS px를 목표로 한다.
- 비교 트레이는 가로 스크롤 가능한 선수 칩을 제공하고 핵심 액션이 뷰포트 밖으로 밀리지 않아야 한다.

### 태블릿/데스크톱: `md` 이상

- 고밀도 테이블을 표시한다.
- 좁은 화면에서는 테이블의 가로 스크롤을 허용하되 선수 열을 고정한다.
- 넓은 화면에서는 최대 콘텐츠 폭을 제한해 지표 간 시선 이동을 안정화한다.

### 공통

- 200% 브라우저 확대에서도 핵심 작업(검색, 필터 초기화, 비교, 저장)이 가능해야 한다.
- 긴 선수명, 번역 문자열, 4명 비교가 레이아웃을 깨뜨리지 않아야 한다.

## 8. 접근성 요구사항

- 페이지는 하나의 명확한 `h1`과 의미 있는 landmark를 가진다.
- 테이블에 caption, 열 헤더 `scope="col"`, 행 헤더 `scope="row"`를 제공한다.
- 모든 버튼/입력/select는 키보드로 조작 가능하고 눈에 보이는 focus indicator를 가진다.
- 토글 버튼은 `aria-pressed`로 상태를 전달한다.
- 아이콘 단독 버튼은 선수명과 동작을 포함한 접근 가능한 이름을 가진다.
- 툴팁 트리거와 설명은 `aria-describedby`로 연결한다.
- 상태 피드백은 `aria-live="polite"`로 전달한다.
- 본문/컨트롤 텍스트는 WCAG AA 대비를 목표로 한다. 네온 색상은 장식적 발광과 실제 텍스트 대비를 구분해 검증한다.
- `prefers-reduced-motion` 사용자는 불필요한 확대/전환을 줄일 수 있어야 한다.
- 포인터 hover만으로 필수 정보를 제공하지 않는다.

## 9. 비기능 요구사항

### 성능

- 초기 샘플 데이터 기준 사용자 입력에 즉각 반응해야 한다.
- 이미지에는 `loading="lazy"`, 적절한 고정 크기, 가능하면 `decoding="async"`를 적용한다.
- 데이터가 수백 명으로 커질 가능성을 고려해 필터/정렬은 memoize하고 행 컴포넌트 분리를 허용한다.
- 현재 릴리스에 가상화 도입은 필수가 아니지만, 500명 이상 실데이터가 확정되면 재평가한다.

### 유지보수성

- TypeScript strict 검사를 통과해야 한다.
- 거대한 단일 컴포넌트를 검색바, 범례, 선수 테이블/카드, 비교 트레이 등 책임 단위로 분리한다.
- 지표 메타데이터와 점수 임계값은 단일 소스에서 관리한다.
- 사용자 노출 문자열은 올바른 UTF-8 한국어로 저장하고 깨진 문자열이 없어야 한다.

### 안정성

- 외부 이미지 실패, localStorage 실패, 비정상 데이터가 전체 화면 crash로 이어지지 않아야 한다.
- 모든 목록 렌더링 키는 안정적인 `player.id`를 사용한다.
- 프로덕션 빌드와 타입 검사가 성공해야 한다.

### 시각 품질

- 다크 배경, 제한된 네온 그린 포인트, 타이트한 행 간격을 유지한다.
- FUTBIN의 정보 밀도는 참고하되 로고, 고유 장식, 레이아웃을 복제하지 않는다.
- 장식보다 빠른 스캔, 숫자 정렬, 일관된 간격을 우선한다.

## 10. 현재 구현 대비 Gap 분석

### 이미 구현된 항목

- 데스크톱 고밀도 테이블과 모바일 카드 전환.
- 선수/클럽/리그/국가 통합 검색 및 악센트 정규화.
- 포지션, 관심선수 필터, 3종 정렬, 활성 필터 칩과 초기화.
- 점수 색상, 범례, 지표 툴팁.
- `<img>` 기반 티어 및 마이크로 에셋.
- 2~4명 비교 선택, 고정 트레이, 상세 비교.
- localStorage 기반 관심선수 복원.
- 기본 table semantics, focus ring, `aria-pressed`, live region.

### P0 — 다음 구현에서 반드시 해결

1. **표시 문자열 무결성 검증**: 소스가 UTF-8이지만 현재 콘솔 기본 인코딩에서는 mojibake처럼 보인다. 실제 브라우저 렌더링에서 한국어와 선수명(`Mbappé`, `Gyökeres`, `Martínez`, `Šeško`, `Giménez`)이 정확한지 테스트하고 잘못 저장된 리터럴이 있으면 복구한다.
2. **이미지 실패 fallback**: 현재 외부 placeholder가 실패하면 깨진 이미지가 그대로 나타난다. 페이스온/마이크로 에셋/티어별 대체 표시와 레이아웃 안정성이 필요하다.
3. **비교 상태 불변식**: 비교 선수를 2명 미만으로 줄였을 때 열린 상세 패널이 상태상 계속 `true`일 수 있다. 패널을 자동으로 닫고 disabled/expanded 상태를 일치시킨다.
4. **실행 가능한 회귀 검증**: 검색, 필터, 관심선수 영속성, 2~4명 비교, 모바일 레이아웃을 테스트 가능한 경계로 분리하고 최소 자동 검증 또는 명시적인 QA 체크를 남긴다.

### P1 — 품질 및 실제 사용성 개선

1. **컴포넌트 분리**: 600줄 안팎의 단일 컴포넌트를 데이터/도메인, 검색·필터, 테이블, 모바일 카드, 비교 트레이로 분리한다.
2. **데이터 주입 경계**: 샘플 `players` 상수를 UI 밖으로 이동하고 props 기반 주입을 허용한다.
3. **이미지 성능**: `decoding="async"`, 고정 dimensions/비율, 오류 처리 추가.
4. **접근성 세부 개선**: 비교 트레이 토글에 `aria-expanded`/`aria-controls`, 닫히는 피드백의 중복 live-region 정리, tooltip ID의 행별 유일성 보장.
5. **모바일 정보 동등성**: 모바일 카드에서 숨겨진 pressing/progression 값이 상세 비교 전에 접근 가능한지 검토하고, 확장 UI 또는 전체 지표 요약을 제공한다.
6. **색상 범위 중앙화**: 임계값, 라벨, 클래스가 서로 어긋나지 않도록 단일 설정으로 관리한다.
7. **축소 모션**: hover 확대와 transition에 reduced-motion 대응 추가.

### P2 — 후속 확장

1. URL query parameter로 검색/필터/정렬 상태 공유.
2. 열별 정렬과 다중 필터(리그, 국가, 나이, 최소 출전시간).
3. 수백~수천 행을 위한 서버 검색/페이지네이션 또는 가상화.
4. 관심선수 계정 동기화와 비교 세션 저장.
5. 선수 상세 페이지, CSV 내보내기, 데이터 업데이트 시각화.
6. 다국어 번역 체계와 지역화된 숫자 포맷.

## 11. 수용 기준

### 검색/필터

- [ ] `Mbappe` 입력 시 `Kylian Mbappé`가 결과에 남는다.
- [ ] 클럽, 리그, 국가 이름으로 검색할 때 일치 선수만 표시된다.
- [ ] 검색 + 포지션 + 관심선수 조건이 AND로 결합된다.
- [ ] 활성 칩 제거와 전체 초기화가 각각 올바른 기본 상태로 돌아간다.
- [ ] 결과 없음 화면에서 전체 초기화를 실행하면 전체 목록이 복구된다.

### 목록/표현

- [ ] 90, 80, 70, 69 경계값이 각각 정의된 네 가지 색상 구간으로 렌더링된다.
- [ ] 모든 선수 행에 페이스온, 국기, 리그, 클럽, 포지션, 티어 이미지가 표시된다.
- [ ] 이미지 로드 실패 후에도 선수명, 점수, 액션과 행 높이가 유지된다.
- [ ] 마우스 hover와 키보드 focus에서 해당 행/컨트롤을 식별할 수 있다.
- [ ] 지표 툴팁은 마우스와 키보드 모두로 열리고 설명을 읽을 수 있다.

### 비교

- [ ] 첫 번째 선수를 선택하면 트레이가 나타나고 상세 비교 액션은 disabled다.
- [ ] 두 번째 선수를 선택하면 상세 비교가 가능하다.
- [ ] 최대 4명까지 선택되며 다섯 번째 선택은 상태 변경 없이 알림을 표시한다.
- [ ] 트레이와 원본 행/카드의 선택 상태가 항상 일치한다.
- [ ] 선택을 1명 이하로 줄이면 상세 패널이 자동으로 닫힌다.
- [ ] 개별 제거와 전체 제거가 키보드로 동작한다.

### 관심선수

- [ ] 추가/제거 시 버튼 상태와 상태 메시지가 즉시 갱신된다.
- [ ] 새로고침 후 유효한 관심선수만 복원된다.
- [ ] localStorage에 잘못된 JSON이 있어도 앱이 렌더링된다.
- [ ] 관심선수만 보기에서 0명인 경우 복구 가능한 빈 상태가 나타난다.

### 반응형/접근성

- [ ] 320px 폭에서 가로 페이지 overflow 없이 검색, 카드 액션, 비교 액션을 사용할 수 있다.
- [ ] `md` 이상에서 테이블과 고정 선수 열이 동작한다.
- [ ] Tab 키만으로 검색→필터→목록 액션→비교 트레이를 사용할 수 있다.
- [ ] 아이콘 단독 버튼이 스크린리더에서 선수명과 동작으로 식별된다.
- [ ] WCAG AA 대비 점검에서 일반 텍스트와 컨트롤이 통과한다.
- [ ] 200% 확대에서도 핵심 사용자 플로우가 차단되지 않는다.

### 빌드/품질

- [ ] `pnpm build`가 오류 없이 완료된다.
- [ ] 브라우저 콘솔에 React key/hydration/runtime 오류가 없다.
- [ ] 사용자 노출 한국어와 라틴 확장 문자가 실제 브라우저에서 깨지지 않는다.
- [ ] 핵심 상태 변환 또는 사용자 플로우에 대한 자동 테스트나 재현 가능한 QA 체크리스트가 있다.

## 12. Out of scope

- 실제 스카우팅 API/데이터베이스 연결 및 서버 상태 관리.
- 로그인, 권한, 조직별 계정, 클라우드 관심선수 동기화.
- 선수 상세 페이지와 라우팅.
- 선수 영입 추천 알고리즘 또는 M.E.S.S.I. 점수 계산식 변경.
- 에셋 크롤러 실행, 저작권/초상권/상표권의 최종 법적 승인.
- 운영 배포, 분석 도구, 오류 모니터링 연결.
- FUTBIN의 상표, 고유 그래픽, 카드 디자인 또는 소스 코드 복제.

## 13. 승인 필요 여부와 설계 단계 전달사항

현재 범위 안에서 사용자 승인이 필요한 중대한 변경은 없다. 설계·구현은 다음 기본 결정으로 진행할 수 있다.

- 기존 다크/네온 고밀도 방향을 유지한다.
- 새로운 대형 기능을 추가하지 않고 P0와 P1 중 구조·접근성·반응형 신뢰성을 우선한다.
- 61~69점은 연속적인 색상 구간을 위해 빨간색으로 처리한다.
- 샘플 데이터는 유지하되 UI에서 분리하고 주입 가능하게 만든다.

실제 API 선택, 계정 기반 저장, 라우팅/상세 페이지, 운영 배포가 이번 파이프라인에 포함되어야 한다면 이는 중대한 범위 확장이므로 구현 전에 사용자 승인이 필요하다.
